抽象構文木

構文解析は、位置情報付きトークン列を、プログラムの階層構造を表す抽象構文木へ変換します。 抽象構文木では、括弧、区切り記号、予約語そのものを保持するのではなく、 宣言、式、パターン、型、モジュールなどの意味のある構造をノードとして保持します。

  • 位置情報付きトークン列
  • ↓ 構文解析・優先順位処理
  • 名前解決前の抽象構文木
  • ↓ 名前解決
  • 解決済み抽象構文木
  • ↓ 型推論
  • 型付き抽象構文木

入力と出力

項目内容
入力token.htmlで定義した位置情報付きトークン列
出力名前が文字列または未解決パスのまま格納された抽象構文木
処理文法の認識、演算子優先順位、結合方向、関数適用、括弧構造の決定
失敗予期しないトークン、閉じ記号の不足、宣言や式の不足、禁止された構文

抽象構文木で保持する情報

情報用途
ノードの種類宣言、式、パターン、型などの構造を表す
子ノード部分式、部分パターン、型引数、宣言列を保持する
未解決名値名、型名、コンストラクタ名、フィールド名、モジュールパスを名前解決へ渡す
リテラル値整数、浮動小数点数、文字、文字列、真偽値、単位値を保持する
ソース位置名前解決、型推論、後続変換のエラー報告に使用する

位置付きノード

type 'a located = {
    desc : 'a;
    span : span;
}

各主要ノードは、先頭トークンの開始位置から末尾トークンの終了位置までを表す spanを持ちます。括弧で囲まれた式では、外側の括弧を含む位置を保持します。

名前とパス

構文内部表現例
非修飾名Longident [name]x、tree、Some
修飾名Longident [module1; ...; name]String.length、A.B.t
モジュールパスLongident [module1; ...; moduleN]A、A.B.C
 
type longident = string list

構文解析ではパスの各要素を文字列として保持します。 各部分が本当にモジュールか、末尾が値、型、コンストラクタのどれかは名前解決で決定します。

再帰性

type rec_flag =
    | Nonrecursive
    | Recursive

andで結ばれた定義は、一つのValueDefinitionまたは TypeDefinitionの中に列として保持します。 再帰グループのスコープ規則は名前解決で適用します。

値束縛

type value_binding = {
    pattern : pattern;
    expression : expression;
    binding_span : span;
}

関数定義の糖衣構文は、構文解析時に無名関数へ変換します。 これにより、トップレベルと局所の関数定義を通常の値束縛として統一して扱えます。

条件式

ソース抽象構文
if e1 then e2 else e3IfThenElse (e1, e2, e3)

基本仕様ではelseを必須とします。 if e1 then e2を許可する場合は、構文解析時に IfThenElse (e1, e2, Unit)へ変換し、型検査でe2 : unitを要求します。

局所定義

ソース抽象構文

無名関数と関数適用

ソース抽象構文

カリー化と左結合は抽象構文木の形で明示します。 複数引数専用の関数ノードや適用ノードは使用しません。

レコード

ソース抽象構文
{ x = e1; y = e2 }Record [(["x"], e1); (["y"], e2)]
e.xField (e, ["x"])

フィールド名がどのレコード型に属するかは抽象構文木では決定しません。 名前解決は候補を収集し、必要な場合は型推論が対象レコード型を確定します。

コンストラクタ

ソース抽象構文
NoneConstructor (["None"], None)
Some eConstructor (["Some"], Some e)
M.Some eConstructor (["M"; "Some"], Some e)

コンストラクタが複数の引数を取る場合、引数は組として一つの式にします。 C (e1, e2)はConstructor (C, Some (Tuple [e1; e2]))になります。

リスト

ソース構文解析直後後続の脱糖候補
[]List []Constructor ([], None)
[e1; e2; e3]List [e1; e2; e3]e1 :: (e2 :: (e3 :: []))
e1 :: e2Cons (e1, e2)組込みconsコンストラクタ

エラー位置と元の表記を保つため、名前解決前ASTではListとConsを保持します。 Core変換までに通常のコンストラクタへ脱糖します。

match式

type case = {
    case_pattern : pattern;
    case_guard : expression option;
    case_body : expression;
    case_span : span;
}
ソース抽象構文
match e with p -> bodyMatch (e, [{ pattern = p; guard = None; body }])
match e with p when g -> bodyMatch (e, [{ pattern = p; guard = Some g; body }])
先頭の|省略可能な区切りであり、ASTには残さない

逐次実行と参照

ソース抽象構文

ref、!、:=をプリミティブ適用として表すこともできますが、 値制限と副作用判定を明確にするため、名前解決前ASTでは専用ノードを使用します。

構文上の糖衣と保持方針

構文ASTでの方針理由
複数引数関数構文解析時に一引数Functionへ変換するカリー化を直ちに明示できる
複数引数適用構文解析時に左結合Applyへ変換する適用規則を単純化できる
リストリテラルListとして保持する元の位置と診断を保ち、Core変換で脱糖する
参照操作専用ノードとして保持する副作用と値制限を明示できる
short-circuit演算専用primitiveとして保持する評価順序を失わない
for、while専用ノードとして保持する型検査と診断後にCoreへ脱糖する
括弧構造決定後は除去する意味のない具象構文だから
先頭の|除去する分岐区切りであり意味を持たない

エラー例報告内容
予期しないトークンlet = 1実際のトークンと期待したパターンまたは識別子
式の不足let x ==の後に式が必要であること
閉じ括弧の不足(x + 1開き括弧位置とEOF位置
閉じ角括弧の不足[1; 2リスト開始位置と期待する]
閉じ波括弧の不足{ x = 1レコード開始位置と期待する}

構文解析後に成立する条件

  • トークン列全体が一つのプログラムとして消費されている
  • EOFより前に未消費トークンが残っていない
  • 括弧、角括弧、波括弧、struct/end、sig/endが対応している
  • 各演算子の優先順位と結合方向がASTの親子関係へ反映されている
  • 関数適用が左結合のApplyへ変換されている
  • 複数引数関数が一引数のFunctionの入れ子へ変換されている
  • 複数の非再帰定義と相互再帰定義が一つの束縛グループとして保持されている
  • すべての主要ノードが元ソース上の位置範囲を持つ
  • 識別子と修飾名が文字列のパスとして保持されている
  • 名前解決前に値名、型名、フィールド名の参照先が勝手に確定されていない
  • リテラルが型に依存しない定数ノードとして保持されている
  • パターンと式の構文が別のノード型として区別されている
  • 型式が式とは別の構文木として保持されている
  • モジュール式、モジュール型、シグネチャ項目が区別されている
  • 構文上許可されない再帰束縛や代入左辺が拒否されている
  • 名前解決、型推論、脱糖で必要な元の構文情報が保持されている
