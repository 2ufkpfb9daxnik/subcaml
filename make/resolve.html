名前解決

名前解決は、構文解析後の抽象構文木に含まれる名前について、 それぞれがどの定義を参照するかを決定する処理です。 同じ文字列の名前でも、定義された位置とスコープが異なれば、 別の識別子として扱います。

  • ソースコード
  • ↓ 字句解析・構文解析
  • 名前付き抽象構文木
  • ↓ 名前解決
  • 解決済み抽象構文木
  • ↓ 型推論
  • 型付き抽象構文木

名前解決では型の正しさを判定しません。 変数、型、コンストラクタ、レコードフィールド、モジュールなどの 参照先を確定し、未定義名、重複定義、不正なスコープ、 ORパターンの束縛不一致などを検出します。

名前解決の入力と出力

段階 名前の表現 例
名前解決前 ソースコードに書かれた文字列 x、map、Some、M.t
名前解決後 宣言ごとに一意な識別子 ValueId(17)、 TypeId(4)、 ConstructorId(9)

解決済み識別子には、表示用の元の名前と、 コンパイラ内部で一意な番号の両方を保持します。 

type value_id = {
    id : int;
    name : string;
}

type type_id = {
    id : int;
    name : string;
}

type constructor_id = {
    id : int;
    name : string;
}

名前空間

名前の種類ごとに独立した名前空間を使用します。 同じ文字列でも、異なる名前空間に属する名前は共存できます。

名前空間 定義する構文 参照する構文
値 let、 関数の仮引数、 パターン変数、 external 変数式、関数適用、値として使用する演算子
型 type t = ... t、M.t、型注釈
型変数 型宣言の型引数、明示的な型変数の束縛 'a、'bなどの型変数
コンストラクタ ヴァリアント型、例外型の定義 コンストラクタ式、コンストラクタパターン
レコードフィールド レコード型定義 レコード作成、フィールド参照、 レコード更新、レコードパターン
モジュール module M = ... M.x、M.t、 open M、include M
発展　モジュール型 module type S = ... モジュール型注釈、ファンクタの引数型
発展　エフェクトコンストラクタ type _ Effect.t += C : ... perform C、エフェクトパターン

値名 tと型名 tは共存できます。 一方、同じスコープの同じ名前空間に同じ名前を二重に定義した場合は、 その宣言形式が明示的に再定義を許可しない限りエラーとします。

解決環境

名前解決中の環境を Γと表します。 環境は名前空間ごとの対応表と、現在開かれているモジュールを保持します。 

type environment = {
    values : value_id NameMap.t;
    types : type_id NameMap.t;
    type_variables : type_variable_id NameMap.t;
    constructors : constructor_id NameMap.t;
    fields : field_id list NameMap.t;
    modules : module_id NameMap.t;
    module_types : module_type_id NameMap.t;
    opened_modules : module_id list;
}
環境の要素 内容
values 非修飾の値名から値識別子への対応
types 非修飾の型名から型識別子への対応
type_variables 現在の型宣言または型注釈内で束縛された型変数
constructors 非修飾のコンストラクタ名からコンストラクタ識別子への対応
fields フィールド名から候補となるフィールド識別子の一覧への対応
modules 非修飾のモジュール名からモジュール識別子への対応
module_types モジュール型名からモジュール型識別子への対応
opened_modules 現在のスコープで開かれているモジュールを新しい順に保持する

モジュール環境

各モジュールは、外部から参照できる名前をまとめたモジュール環境を持ちます。 

type module_environment = {
    values : value_id NameMap.t;
    types : type_id NameMap.t;
    constructors : constructor_id NameMap.t;
    fields : field_id list NameMap.t;
    modules : module_id NameMap.t;
    module_types : module_type_id NameMap.t;
}

モジュールの型検査より前の名前解決では、 モジュール環境は主に構造上存在する宣言を表します。 値の型、型別名の展開結果、モジュール型との適合性は、 後続の型検査で決定します。

組込み環境

プログラムの名前解決は、組込みの型、値、コンストラクタ、 モジュールを登録した初期環境から開始します。

分類 主な組込み名
プリミティブ型 int、 bool、 float、 char、 string、 unit
型構築子 list、ref
定数コンストラクタ []、()、true、false
組込み値 プリミティブ演算、 ref、 必要なランタイム関数
組込みモジュール String
発展　型構築子 array、exn
発展　組込みモジュール Array、Effect

解決済み抽象構文木

名前解決後の抽象構文木では、宣言と参照に一意な識別子を格納します。 ソース位置と元の名前も、エラー表示のために保持します。

名前解決前 名前解決後
Variable "x" Variable ValueId(17, "x")
TypeName "tree" TypeName TypeId(4, "tree")
Constructor "Node" Constructor ConstructorId(9, "Node")
Field "value" 一意なら Field FieldId(3, "value")、 型情報が必要なら候補集合を保持する
ModulePath ["A"; "B"] ModulePath [ModuleId(2, "A"); ModuleId(8, "B")]

名前解決の記法

記法 意味
Re⟦ Γ; e⟧ 環境 Γで式 eを解決する
Rp⟦ Γ; p⟧ パターン pを解決し、 解決済みパターンと新しい束縛の集合を返す
RT⟦ Γ; T⟧ 型式 Tに含まれる型名と型変数を解決する
Rd⟦ Γ; d⟧ 宣言 dを解決し、 解決済み宣言と後続宣言用の環境を返す
Rm⟦ Γ; m⟧ モジュール式を解決する

名前の探索順序

非修飾名 xは、次の順序で探索します。

優先順位 探索先
1 現在の最も内側の局所スコープ
2 外側の局所スコープを内側から外側へ順番に探索する
3 現在のストラクチャでそれ以前に定義された名前
4 openされたモジュールを、 最後に開いたものから逆順に探索する
5 組込み環境

修飾名 M.xは、まずモジュール名 Mをモジュール名前空間で解決し、 そのモジュール環境から xを探索します。 修飾名の探索には openによる非修飾候補を使用しません。

シャドーイング

内側のスコープで同じ名前を定義した場合、 そのスコープ内では外側の定義を隠します。 隠された定義自体は削除されません。

ソース 解決結果 
let x = 1 in
let x = 2 in
x
 最初の xを x#1、 二番目の xを x#2とすると、 最後の参照は x#2を指す

シャドーイングはエラーにしません。 必要なら未使用定義や意図しないシャドーイングとして警告できます。

式の名前解決

名前解決前 名前解決後 環境の扱い
c 同じ定数c 環境を参照しない
x Γの値名前空間から得た ValueId 見つからなければ未定義値エラー
M.x モジュール Mの環境から得た ValueId モジュールと値を順番に解決する
op( e1, ... , en) 演算子の組込み識別子と Re⟦Γ; e1⟧ ... 各部分式を同じ環境で解決する
if e1 then e2 else e3 各部分式を解決した条件式 三つの部分式を同じ環境で解決する
e1 e2 ... en 関数位置と各実引数を解決した関数適用 すべて同じ環境で解決する
fun p1 ... pn -> e 解決済みパターンと本体 各引数パターンの束縛を順番に環境へ追加してから 本体を解決する
match e with ... 対象式、各パターン、ガード、分岐本体を解決した式 各分岐は外側の環境から独立に開始し、 その分岐のパターン束縛だけを追加する
for x = e1 to e2 do e3 done ループ変数へ新しい ValueIdを割り当てたループ 境界式は外側の環境で解決し、 本体だけをループ変数を追加した環境で解決する
(e : T) 解決済み式と解決済み型注釈 式と型を対応する名前空間で解決する

非再帰局所定義の解決

名前解決前 解決手順 重要な規則
let p = e1 in e2
  1. e1を 元の環境 Γで解決する
  2. pを解決して新しい束縛 Δを得る
  3. Γ + Δで e2を解決する
パターンで定義される名前は、 e1の中では使用できない

非再帰関数定義の解決

名前解決前 解決手順 スコープ
let f p1 ... pn = e1 in e2
  1. 関数名 fへ新しい ValueIdを作る
  2. 仮引数パターンを解決して束縛 Δを得る
  3. Γ + Δで 関数本体 e1を解決する
  4. Γ + {f}で 後続式 e2を解決する
非再帰定義なので fは自身の本体から参照できない

再帰関数定義の解決

名前解決前 解決手順 スコープ
let rec f p1 ... pn = e1 in e2
  1. 関数名 fへ新しい ValueIdを作る
  2. fを環境へ追加する
  3. 仮引数パターンを解決する
  4. Γ + {f} + Δで 関数本体 e1を解決する
  5. Γ + {f}で 後続式 e2を解決する
fは自身の本体と後続式から参照できる

相互再帰関数定義の解決

名前解決前 解決手順 スコープ
let rec f1 ... = e1 and ... and fn ... = en in e
  1. すべての関数名 f1から fnへ 一意な識別子を先に割り当てる
  2. すべての関数名を共通環境へ追加する
  3. 各関数について、その関数固有の仮引数を追加して 本体を解決する
  4. 後続式を共通環境で解決する
 同じ相互再帰グループのすべての関数が、 すべての関数本体から参照できる

複数の非再帰定義

名前解決前 解決順序 規則
let p1 = e1 and ... and pn = en すべての右辺を元の環境 Γで独立に解決し、 すべてのパターン束縛を右辺の解決後に環境へ追加する 同じ非再帰グループの右辺から、 そのグループで新しく定義される名前を参照できない

パターンの名前解決

パターンの名前解決は、 パターン内で新しく定義される値識別子の集合も返します。 パターンに現れる変数は参照ではなく定義です。

パターン 解決結果 新しい束縛
_ ワイルドカード なし
x 新しい ValueIdを持つ変数パターン {x}
c 同じ定数パターン なし
( p1, ... , pn) 各要素を解決したタプルパターン 各要素の束縛の互いに素な和集合
{ l1 = p1; ... } フィールド候補と各部分パターンを解決したパターン 各部分パターンの束縛の和集合
C 解決済みコンストラクタ識別子 なし
C p 解決済みコンストラクタと解決済み引数パターン 引数パターンの束縛
[] 組込みの空リストコンストラクタ なし
p1 :: p2 組込みのconsコンストラクタを使用するパターン 両方の部分パターンの束縛の和集合
p as x 部分パターンを解決し、 xへ新しい識別子を割り当てる 部分パターンの束縛と x
( p : T) 解決済みパターンと解決済み型注釈 部分パターンの束縛

パターン内の重複束縛

一つのパターン内で同じ名前を複数回束縛することはできません。

パターン 結果
(x, y) 有効。xとyを別々に束縛する
(x, x) エラー。同じパターン内でxを二重に束縛している
Some x as y 有効。xとyを束縛する
Some x as x エラー。別名が既存のパターン変数と重複している

ORパターン

ORパターンの両側は、同じ名前の集合を束縛しなければなりません。 対応する名前には、両側で共通の解決済み識別子を割り当てます。

パターン 結果
Some x | Error x 有効。両側の xを同じ ValueIdへ解決する
Some x | None エラー。左側だけが xを束縛している
(x, y) | (y, x) 有効。両側が xと yを束縛する

パターンマッチ分岐のスコープ

部分 使用する環境
マッチ対象式 外側の環境Γ
各分岐のパターン 外側の環境Γ
各分岐のガード 外側の環境に、その分岐のパターン束縛を追加した環境
各分岐の本体 外側の環境に、その分岐のパターン束縛を追加した環境
別の分岐 前の分岐のパターン束縛を引き継がず、 外側の環境から開始する

型式 解決結果
プリミティブ型π 組込みの型識別子
型変数α 現在の型変数環境にある型変数識別子
T1 -> T2 両方の型を再帰的に解決した関数型
T1 * ... * Tn 各要素型を解決したタプル型
T list 組込みのlist型識別子と解決済み引数型
T ref 組込みのref型識別子と解決済み引数型

M.t モジュールM内の型識別子

(module S) 発展　解決済みモジュール型識別子

型変数の解決

型宣言の左辺に書かれた型変数は、 その型宣言の右辺だけで有効です。

宣言 解決規則
type α t = T αへ新しい型変数識別子を割り当て、 その識別子を使用して Tを解決する
type ( α, β) t = T αと βへ異なる型変数識別子を割り当てる
型引数にない型変数が右辺へ現れる 束縛されていない型変数としてエラーにする
同じ型引数名を複数回書く 重複型引数としてエラーにする

型宣言の解決

型宣言では、型名、コンストラクタ、レコードフィールドを それぞれ対応する名前空間へ登録します。

宣言 登録する名前 解決順序
type t = T 型名t 型名を先に登録し、 その型名を参照できる環境で右辺を解決する
type t = C1 of T1 | ... 型名 tと各コンストラクタ 型名を登録し、各引数型を解決してから コンストラクタを後続環境へ公開する
type t = { l1 : T1; ... } 型名 tと各フィールド名 型名を登録し、各フィールド型を解決してから フィールドを後続環境へ公開する
type t1 = T1 and ... and tn = Tn すべての型名と、 すべてのコンストラクタおよびフィールド すべての型名を先に登録し、 共通環境で各右辺を解決する

コンストラクタの解決

構文 解決規則
C コンストラクタ名前空間から ConstructorIdを取得する
C e Cをコンストラクタとして解決し、 引数式 eを値環境で解決する
M.C モジュール Mのコンストラクタ環境から解決する
同名コンストラクタが複数の開いたモジュールに存在する 最後に開いたモジュールの定義を使用する。 必要なら曖昧な非修飾参照として警告する

レコードフィールドの解決

異なるレコード型が同じフィールド名を持つことを許可する場合、 名前解決だけではフィールドを一意に決められないことがあります。 その場合は候補集合を解決済み抽象構文木へ保持し、 型推論がレコード型を決定した時点で一つへ絞ります。

構文 名前解決の結果
{ x = e1; y = e2 } xと yの候補レコード型の共通部分を求める。 一意なら各 FieldIdを確定し、 複数なら候補を型推論へ渡す
e.x フィールド名 xの候補一覧を保持する
{ e with x = e1 } フィールド候補を保持し、 基礎レコードの型によって型推論時に確定する
e.x <- e1 フィールド候補を保持する。 可変フィールドであるかは型検査で判定する
M.x モジュール M内のフィールド候補だけを使用する

基本実装を単純にする場合は、 プログラム全体でレコードフィールド名を一意にする制限を採用できます。 ただし、モジュールと複数のレコード型を扱う仕様では、 候補集合を型推論で絞る方式のほうが拡張しやすくなります。

トップレベル宣言の解決

ストラクチャ内の宣言は上から順番に解決します。 原則として、後で定義される名前を前の宣言から参照することはできません。

宣言 右辺を解決する環境 後続宣言へ追加する名前
let p = e 宣言前の環境 パターンpが束縛する値
let f p1 ... = e 宣言前の環境と仮引数の束縛 関数名f
let rec f p1 ... = e 関数名fと仮引数を追加した環境 関数名f
let rec f1 = ... and ... すべての再帰関数名を追加した共通環境 すべての関数名
type t = T 型名tを追加した型環境 型名、コンストラクタ、フィールド
external x : T = s 型注釈Tを現在の型環境で解決する 値名x
module M = m モジュール式mを現在の環境で解決する モジュール名M
open M 現在のモジュール環境でMを解決する 新しい定義は作らず、非修飾名の探索対象を追加する
include m モジュール式mを現在の環境で解決する モジュールmが公開する各名前

モジュール定義の解決

モジュール式 解決規則
M 現在のモジュール環境からモジュール識別子を取得する
struct d1 ... dn end 新しい内側の環境を作り、 宣言を上から順番に解決する。 解決後の公開名からモジュール環境を作る
( m : S) モジュール式とモジュール型内の名前を解決する。 適合性は型検査で判定する
functor (X : S) -> m 発展　モジュール型 Sを解決し、 モジュール引数 Xを追加した環境で本体を解決する
m1 ( m2) 発展　両方のモジュール式を解決する。 ファンクタ型との適合性は型検査で判定する

openの解決

open Mは、モジュール Mの公開名を 非修飾名の探索候補へ追加します。 元のモジュール環境や識別子を複製しません。

状況 解決規則
局所定義と開いたモジュールの名前が同じ 局所定義を優先する
複数の開いたモジュールに同じ名前がある 最後に開いたモジュールの名前を優先する
修飾名M.x openの順序に関係なく、指定されたMだけを探索する
開いたモジュールに名前がない 次の候補または組込み環境を探索する
存在しないモジュールを開く 未定義モジュールエラー

includeの解決

include mは、 モジュール式 mの公開内容を 現在のストラクチャの定義として取り込みます。 openとは異なり、取り込んだ名前は現在のモジュールの公開内容にも含まれます。

宣言 非修飾参照に追加 現在のモジュールから再公開
open M はい いいえ
include M はい はい

includeによって現在のスコープにすでに存在する名前と 同じ名前が取り込まれる場合は、重複定義としてエラーにするか、 言語仕様で明示した上書き規則を適用する必要があります。 基本仕様では重複定義エラーとします。

外部関数宣言の解決

名前解決前 名前解決後 処理
external x : T = s 新しい ValueId、 解決済み型 T、 外部名 s 型注釈に含まれる型名を解決し、 値名 xを後続環境へ追加する

演算子を通常の値として再定義できる仕様を採用する場合は、 専用プリミティブノードへ直ちに変換せず、 通常の値名前空間で解決します。 基本仕様では、言語仕様に列挙された演算子を予約済みプリミティブとして扱います。

型推論で 解決

名前だけでは一意に決められず、型情報が必要なものは、 候補を保持して型推論へ渡します。

名前解決の処理順序

段階 処理
1 組込み型、組込み値、組込みモジュールを初期環境へ登録する
2 ソースファイルのトップレベル宣言を上から順番に処理する
3 各宣言が新しく定義する識別子を必要な時点で作成する
4 宣言の右辺、型注釈、パターン、モジュール式を解決する
5 宣言によって後続から見える名前を環境へ追加する
6 未定義名、重複定義、不正なパターン束縛を報告する
7 解決済み抽象構文木と宣言情報を型推論へ渡す

解決済み宣言情報

型推論と後続変換で必要になる宣言情報を、 解決済み抽象構文木とは別の表として保持できます。

情報 内容
値宣言情報 値識別子、元の名前、定義位置、所属モジュール
型宣言情報 型識別子、型引数、型宣言の種類、所属モジュール
コンストラクタ情報 コンストラクタ識別子、所有する型識別子、 引数型構文、宣言順
フィールド情報 フィールド識別子、所有するレコード型、 フィールド型構文、可変性、宣言順
モジュール情報 モジュール識別子、公開する名前、定義位置
外部関数情報 値識別子、外部名、解決済み型注釈

名前解決後に成立する条件

  • すべての値参照が一つの値識別子を指している
  • すべての型名が一つの型識別子を指している
  • すべての型変数参照が有効な型変数識別子を指している
  • すべてのコンストラクタ参照が一つのコンストラクタ識別子を指している
  • レコードフィールド参照が一つのフィールド識別子または型推論用の候補集合を持つ
  • すべてのモジュール参照が一つのモジュール識別子を指している
  • すべての修飾名について、モジュールパスの各要素が解決されている
  • 未定義の名前が解決済み抽象構文木に残っていない
  • 同じ宣言によって束縛された名前が同じ識別子を使用している
  • シャドーイングされた同名の定義が異なる識別子を持っている
  • 非再帰定義の右辺から、その定義自身の名前を参照していない
  • 再帰定義の本体から、同じ再帰グループの名前を参照できる
  • 一つのパターン内に重複した変数束縛が存在しない
  • ORパターンの各選択肢が同じ名前集合を束縛している
  • パターン変数が、そのパターンに対応するガードと分岐本体だけで有効になっている
  • 型宣言の右辺に現れる型変数が、その型宣言の型引数として束縛されている
  • 相互再帰型定義の各右辺から、同じ宣言グループのすべての型を参照できる
  • openによる名前探索の優先順位が確定している
  • includeによって取り込まれた名前が現在の環境とモジュールの公開内容へ追加されている
  • 外部関数宣言の値名、型注釈、外部名が対応付けられている
  • 組込みの型、値、演算子、コンストラクタ、モジュールが組込み識別子へ解決されている
  • レコードフィールドを一意に決定できない場合、型推論で絞り込める候補集合が保持されている
  • 各解決済み識別子に元の名前とソース位置が保持されている
  • 型推論が文字列による名前探索を行わず、解決済み識別子を直接使用できる

次の段階との関係

次の型推論では、名前解決済み抽象構文木を入力として使用します。 型推論器は、変数名や型名を文字列で探索し直さず、 各ノードに格納された一意な識別子をキーとして型環境を参照します。

名前解決から渡す情報 型推論での用途
値識別子 値識別子ごとの型スキームの登録と参照
型識別子 ユーザー定義型、型別名、型構築子の参照
型変数識別子 型注釈と型宣言内の型変数の同一性を保持する
コンストラクタ識別子 コンストラクタの引数型と結果型を具体化する
フィールド識別子または候補集合 レコード型を決定し、フィールドの型と可変性を検査する
モジュール識別子 モジュールが提供する値、型、コンストラクタの型情報を参照する
外部関数情報 明示された型注釈を外部関数の型スキームとして登録する
ソース位置 型エラーの発生位置と関連する宣言位置を報告する

型推論が完了すると、各式、パターン、宣言へ型が付与された 型付き抽象構文木を生成します。 その後、パターンマッチの網羅性検査、脱糖、Core中間表現への変換を行います。
